1. Executive Summary

GoodTracker is a student software project focused on developing a mobile application for reserving shared laboratory and office equipment. During the current project stage, the team’s primary focus has been project initiation, scope definition, planning, and preparation of the M1 deliverables.

The team has established the project’s initial objectives, defined the planned application scope, allocated primary responsibilities, identified initial risks, and documented success criteria. The proposed technical architecture consists of React Native with Expo and TypeScript for the mobile application, Node.js with Express for the backend, and Supabase for database and authentication services.

According to the project README, implementation has not started yet. Therefore, no application functionality is reported as completed in this update. The next priority is to organize the transition from project initiation to the next milestone, confirm task ownership, maintain an up-to-date GitHub project board, and prepare the technical work needed for the planned Android demonstration.

This report documents the known project status and identifies the information that must be verified through GitHub records and team coordination.

3. M1 Deliverables and Planning Outcomes

The M1 preparation established the following project foundations.

3.1 Project Charter and Scope

The project charter defines the purpose of GoodTracker and the intended functionality of the initial Android demonstration.

The planned scope includes sign-in, equipment browsing, search, availability display, reservation requests, cancellation, and staff approval or rejection of reservations.

Payments, university single sign-on, push notifications, and production deployment are outside the initial release scope.

3.2 Delivery Approach

The documented delivery approach uses a hybrid model: predictive governance for academic milestones and agile execution for iterative development.

The team plans to use two-week sprint cycles, GitHub Projects, GitHub Issues, pull requests, peer reviews, and explicit Definition of Done criteria.

3.3 Initial Risk Register

The project documentation identifies several risks requiring continued monitoring:

* Academic workload and examination periods may affect delivery schedules.
* Supabase service limits may constrain development or demonstration activities.
* Concurrent reservation requests may cause booking conflicts if not handled correctly.
* Android screen differences may introduce layout issues.
* Delays in API contracts may block mobile and backend integration.
* Scope expansion may divert effort from the core reservation workflow.

These risks are documented in the M1 planning material. Their current status should be reviewed before the next milestone.

3.4 Success Criteria

The documented success criteria focus on preventing overlapping reservations, enforcing authorization, completing the end-to-end reservation flow, controlling scope, and reviewing code changes.

These are planned verification criteria, not evidence that the application has already passed implementation tests.

7. Board Maintenance and Team Coordination

The project uses GitHub Projects and GitHub Issues to track work.

The documented workflow is:

Backlog → To Do → In Progress → Review/Test → Done

Each task should have a clear owner and expected outcome. Development work should be performed on a branch, submitted through a pull request, and reviewed by another team member.

During weekly maintenance, the team should:

1. Review the status of open issues.
2. Confirm that every active task has an owner.
3. Check that task descriptions include clear expected outcomes.
4. Update task status to reflect actual progress.
5. Identify blocked tasks and record the reason.
6. Link completed work to relevant commits or pull requests.
7. Confirm that the next milestone’s priorities are represented in the backlog.

The actual completion of these maintenance activities should be recorded after they have been performed.
